# B-02 routing spike: Bengaluru pilot

**Status:** complete on 2026-10-07 using Geoapify. The local API key was read from an ignored file and was never printed or committed. Sanitized measurements are stored in `routing-spike-results.json`.

## Pilot routes

The coordinates were resolved through Geoapify geocoding before routing:

- Whitefield, Ramagondanahalli → Kadugodi Tree Park
- Whitefield, Ramagondanahalli → Mahatma Gandhi Road

These are representative development routes, not a stored user's home or live GPS history.

## Observed results

| Route | Mode | Result | Distance | Duration |
|---|---|---:|---:|---:|
| Ramagondanahalli → Kadugodi Tree Park | Walk | Available | 4.37 km | 67 min |
| Ramagondanahalli → Kadugodi Tree Park | Drive, approximated traffic | Available | 4.56 km | 14 min |
| Ramagondanahalli → Kadugodi Tree Park | Scheduled transit | No route | — | — |
| Ramagondanahalli → Kadugodi Tree Park | Approximated transit | Available | 4.48 km | 31 min |
| Ramagondanahalli → Mahatma Gandhi Road | Walk | Available | 15.84 km | 245 min |
| Ramagondanahalli → Mahatma Gandhi Road | Drive, approximated traffic | Available | 17.38 km | 66 min |
| Ramagondanahalli → Mahatma Gandhi Road | Scheduled transit | No route | — | — |
| Ramagondanahalli → Mahatma Gandhi Road | Approximated transit | Available | 15.45 km | 60 min |

The scheduled transit failure was HTTP 400 with `Cannot reach destination - too far from a transit stop`. Approximated transit returned walk and bus instructions, including route numbers and transfers, but did not provide dependable structured platform, stop-coordinate, agency, or schedule data in these responses. Walking and driving returned route geometry, distance, duration, legs, step boundaries, and turn instructions. Approximate driving traffic increased the city-centre ETA, but it is a road-class speed model rather than current congestion.

Observed response latency was below one second for the tested calls. Each request contained one origin-to-destination leg and therefore normally consumes one Geoapify credit. The free plan currently provides 3,000 credits per day and may be used commercially within its limits and attribution rules.

## Provider decision

Use Geoapify behind a provider-neutral backend adapter for the current MVP:

- `walk` for walking suggestions.
- `drive` with `traffic=approximated` for car/auto-like road suggestions. The UI must say road route and must not claim a dedicated auto-rickshaw model or live traffic.
- `approximated_transit` for an **estimated public transport** suggestion. The UI must not describe it as live or schedule-aware.

Do not use Geoapify `transit` as a guaranteed option for this pilot area. B-10 must return a no-route result when a requested mode is unavailable. B-11/F-12 may use route-step boundaries as provisional checkpoints, but metro/platform timing and live service data remain unavailable from the tested response.

Google Routes remains a future adapter candidate when billing activation is acceptable. Its addition must replace infrastructure only; circle rules, selected-route entities, and Flutter models must remain provider neutral.

## Mapping into B-10

Store and expose only the fields the product needs:

- provider route option ID generated by the adapter
- public mode label and accuracy qualifier
- total distance and ETA range
- ordered legs with normalized `walk`, `road`, or `transit` mode
- route geometry for display
- checkpoint coordinates derived from meaningful step/leg boundaries

Raw provider responses should not be returned to Flutter or retained indefinitely. Provider keys stay in backend secrets. Route selection remains explicit; the backend never infers which suggestion a mover chose.
